## Context

I use Spark at work without ever seeing what's underneath the DataFrame API — the scheduler, the shuffle, the part where a map/reduce job actually becomes threads doing work. So I built MiniSpark: a small version of it myself, in C, with Resilient Distributed Datasets and a DAG scheduler, to find out.

## The problem

The interesting part of a system like Spark isn't running one function over one array — it's coordinating many workers pulling from a shared queue, handing results to a reduce stage, and doing it all without a garbage collector or a runtime managing memory for you. Every synchronization primitive is a decision you make explicitly, and every one you get wrong is a race condition or a deadlock, not a stack trace pointing at a framework's internals.

<Decision title="A fixed thread pool over spawning a thread per task" alternatives="spawn/join a new pthread for every unit of work">
Thread creation isn't free, and a naive spawn-per-task design means the OS scheduler is doing work proportional to task count instead of core count. A fixed pool sized to available cores, pulling from a shared work queue, keeps the number of live threads bounded and predictable regardless of how many tasks are actually queued.
</Decision>

<Decision title="A single mutex-guarded work queue over per-worker queues with stealing" alternatives="work-stealing deques, one per worker thread">
Work stealing is the right answer at real scale, but it's also a meaningfully more complex piece of synchronization to get correct. For a framework built to understand the core execution model — not to out-benchmark Spark — a single shared queue behind one mutex kept the concurrency logic legible while still parallelizing real work across every core.
</Decision>

<Decision title="A dedicated reduce stage instead of merging results as workers finish" alternatives="have the last finishing worker perform the reduce inline">
Merging inline means the reduce logic runs on whichever thread happens to finish last — nondeterministic, and it entangles worker code with aggregation code. A separate reduce stage that consumes finished results keeps the two concerns apart and makes the output order deterministic regardless of which worker finishes when.
</Decision>

<Decision title="Lineage recomputation over checkpointing every partition" alternatives="periodically snapshot intermediate results to disk; keep no recovery path at all">
Spark's actual answer to fault tolerance is lineage — remembering how a partition was derived, not saving a copy of it. Checkpointing everything is simpler to implement but pays a constant disk-write tax whether or not a worker ever fails. Recomputing lost partitions from their lineage instead meant paying that cost only when something actually went wrong — recovery landed under 5% overhead instead of a constant tax on every run.
</Decision>

## What I'd do differently

I'd add work stealing once the single-queue version was correct and benchmarked — having a working baseline first would have made it possible to actually measure whether stealing was worth its added complexity, instead of guessing.
